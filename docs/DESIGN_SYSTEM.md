## 1. 브랜드 포지셔닝

### 1-1. 감성 키워드 및 선정 근거

빌라메이트가 전달해야 하는 감성은 세 가지 층위로 구성된다.

**[1] 신뢰 (Trust) — 가장 중요한 감성**

동대표는 이웃의 돈을 관리하는 사람이다. 입주민은 자신의 관리비가 어디에 쓰이는지 확인하고자 한다. 이 서비스가 '카카오톡 단체방'이나 '수기 장부'를 대체하려면, 반드시 공공 기관 수준의 신뢰감을 시각적으로 전달해야 한다. 색상의 파란 계열 선택, 정돈된 레이아웃, 명확한 숫자 표기가 이 감성을 뒷받침한다.

**[2] 단순함 (Simplicity) — 비전문가 사용자를 위한 핵심 원칙**

주요 사용자인 동대표(40~60대)는 앱 사용 경험이 제한적이다. UI의 모든 요소는 "설명 없이도 이해되는가"를 기준으로 설계해야 한다. 기능을 자랑하기보다 필요한 것만 보여주는 절제된 UI가 이 서비스의 차별점이 된다.

**[3] 따뜻한 전문성 (Warm Professionalism) — 브랜드 개성**

공공 기관처럼 딱딱하거나 핀테크처럼 차갑지 않아야 한다. '이웃'이라는 관계에서 발생하는 서비스이기 때문에, 숫자와 금융 정보를 다루면서도 친근하고 사람 냄새가 나는 톤이 필요하다. 이는 폰트 선택(Pretendard — 따뜻하고 읽기 쉬운 산세리프), 일러스트레이션 스타일, 빈 상태 문구 등에서 구현된다.

### 1-2. 경쟁 서비스 분석 및 차별화

| 서비스 | 포지셔닝 | 한계 |
|--------|----------|------|
| 아파트아이, 하이파킹 | 대형 아파트 전용, 관리사무소가 있는 곳 기준 | 빌라·다세대 비적합, 동대표 직접 운영 불가 |
| 카카오톡 단체방 | 실제로 가장 많이 쓰이는 대안 | 히스토리 관리 불가, 미납 추적 불가, 감정 마찰 발생 |
| 당근마켓 동네생활 | 커뮤니티 기능 | 재무 관리 기능 없음 |
| Buildium (미국) | 전문 임대 관리 SaaS | 한국 빌라 구조·관행 미반영, 영문 UI |

**빌라메이트 차별화 포인트**
- 동대표 1인이 독립적으로 운영할 수 있는 유일한 도구
- 청구서 발행 → 독촉 → 수납 확인이 하나의 플로우로 연결
- 입주민에게 장부·투표 결과를 투명하게 공개하는 신뢰 구조
- 카카오 알림톡 연동으로 앱 미설치자도 청구서 확인 가능

### 2-7. 다크모드 지원 여부

**Phase 1: 다크모드 미지원. Light mode 전용.**

## 3. 타이포그래피

### 3-1. 폰트 패밀리

**한국어 본문: Pretendard**
- 출처: GitHub 오픈소스 (naver/pretendard). 무료 상업 사용 가능.
- 선정 근거: 한국어 산세리프 중 가장 가독성이 높고, 숫자 자형이 명확하다 (1과 l, 0과 O 구분이 명확). 중장년층 가독성을 위해 자간이 넉넉하고 획이 두렷하다. React Native에서 커스텀 폰트로 로드 가능.
- Fallback: `Apple SD Gothic Neo` (iOS), `Noto Sans KR` (Android 웹뷰)

**영문·숫자 혼합: Pretendard 단일 적용**
- Pretendard의 영문·숫자 자형이 충분히 안정적이므로 별도 영문 폰트를 분리하지 않는다.
- 단, 대형 금액 표시(청구서 총액 등)의 경우 `font-variant-numeric: tabular-nums`를 적용해 숫자 폭을 균일하게 유지한다.

**백오피스 웹: Pretendard (동일) + Inter (영문 전용 숫자 집약 테이블)**
- 백오피스의 데이터 테이블에서는 Inter를 숫자 전용으로 병행 사용해 숫자 정렬 가독성을 높인다.

### 3-2. 타이포그래피 스케일

모든 단위는 px 기준. React Native에서는 동일 수치를 `sp` 없이 숫자로 적용 (RN은 기본이 dp, 실질적으로 px 근사).

#### Display

| 이름 | font-size | line-height | font-weight | letter-spacing | 사용처 |
|------|-----------|-------------|-------------|----------------|--------|
| `display-lg` | 32px | 40px (1.25) | 700 (Bold) | -0.5px | 온보딩 타이틀, 랜딩 헤드라인 |
| `display-sm` | 28px | 36px (1.29) | 700 | -0.3px | 빈 상태 메인 카피 |

#### Heading

| 이름 | font-size | line-height | font-weight | letter-spacing | 사용처 |
|------|-----------|-------------|-------------|----------------|--------|
| `heading-1` | 24px | 32px (1.33) | 700 | -0.2px | 화면 타이틀 (스크린 헤더) |
| `heading-2` | 20px | 28px (1.4) | 600 (SemiBold) | -0.1px | 섹션 헤더, 카드 타이틀 |
| `heading-3` | 18px | 26px (1.44) | 600 | 0px | 서브섹션, 모달 타이틀 |

#### Body

| 이름 | font-size | line-height | font-weight | letter-spacing | 사용처 |
|------|-----------|-------------|-------------|----------------|--------|
| `body-lg` | 17px | 26px (1.53) | 400 (Regular) | 0px | 게시판 본문, 긴 설명 텍스트 |
| `body-md` | 15px | 23px (1.53) | 400 | 0px | **기본 본문 (가장 많이 쓰임)** |
| `body-sm` | 13px | 20px (1.54) | 400 | 0.1px | 보조 설명, 메타 정보 |

#### Caption & Label

| 이름 | font-size | line-height | font-weight | letter-spacing | 사용처 |
|------|-----------|-------------|-------------|----------------|--------|
| `caption` | 12px | 18px (1.5) | 400 | 0.2px | 날짜, 상태 보조 텍스트 |
| `label-md` | 15px | 20px (1.33) | 600 | 0px | 버튼 텍스트, 탭 라벨 |
| `label-sm` | 13px | 18px (1.38) | 600 | 0px | 작은 버튼, 뱃지 텍스트 |
| `number-lg` | 28px | 36px (1.29) | 700 | -0.5px | 미납 총액 등 핵심 수치 |
| `number-md` | 20px | 28px (1.4) | 700 | -0.3px | 청구서 금액 |
| `number-sm` | 15px | 22px (1.47) | 600 | -0.1px | 테이블 내 금액 |

**Number 스케일 별도 정의 이유:** 관리비·금액 수치는 서비스의 핵심 정보다. 일반 Body 텍스트와 시각적으로 분리되어야 동대표와 입주민이 "얼마"를 즉시 파악할 수 있다. `tabular-nums` 속성 필수 적용.

**최소 텍스트 크기 규칙:** 화면에 표시되는 모든 텍스트는 최소 12px (Caption) 이상. 접근성 고려 시 주요 인터랙션 요소(버튼, 탭 라벨)는 최소 15px.

## 4. 간격 & 레이아웃 (Spacing & Layout)

### 4-1. Base Unit

**Base Unit: 4px**

모든 간격은 4px의 배수로 정의한다. 이는 Tailwind CSS의 기본 단위(0.25rem = 4px)와 일치하여 Tailwind 클래스를 그대로 디자인 토큰으로 사용할 수 있다.

### 4-2. Spacing Scale

| 토큰 | px 값 | Tailwind 클래스 | 사용처 |
|------|--------|-----------------|--------|
| `space-1` | 4px | `p-1`, `m-1` | 아이콘과 텍스트 간 미세 간격 |
| `space-2` | 8px | `p-2`, `gap-2` | 뱃지 내부 padding, 인라인 아이콘 간격 |
| `space-3` | 12px | `p-3` | 작은 카드 내부 padding |
| `space-4` | 16px | `p-4` | **기본 컴포넌트 padding (버튼, 입력 필드)** |
| `space-5` | 20px | `p-5` | 섹션 간 간격 (중간) |
| `space-6` | 24px | `p-6` | **카드 내부 padding (기본 카드)** |
| `space-8` | 32px | `p-8` | 화면 최상단 여백, 대형 섹션 간격 |
| `space-10` | 40px | `p-10` | 온보딩 버튼 하단 여백 |
| `space-12` | 48px | `p-12` | 탭 바 높이 기준 |

**8px 리듬 원칙:** 섹션과 섹션 사이, 카드와 카드 사이는 반드시 8px 배수(16, 24, 32px)를 사용한다. 4px는 컴포넌트 내부 미세 조정에만 허용한다.

### 4-3. 모바일 레이아웃 그리드

**기준 디바이스:** iPhone 14 (390 x 844pt) 기준 설계, 375px 이상 전 기기 대응.

| 항목 | 값 | 비고 |
|------|----|------|
| Screen 좌우 Padding | 16px | `px-4` — 콘텐츠 영역 기준 |
| 최대 콘텐츠 폭 | 제한 없음 (전체 너비) | 모바일 전용이므로 max-width 불필요 |
| 탭 바 높이 | 56px + Safe Area Inset | 아이콘 24px + 라벨 12px + 여백 |
| 스크린 헤더 높이 | 56px | 뒤로가기 + 타이틀 + 우측 액션 |
| 카드 간 여백 | 12px | 동일 섹션 내 카드들의 `gap` |
| 섹션 간 여백 | 24px | 서로 다른 섹션 구분 |
| 리스트 아이템 최소 높이 | 56px | 터치 타깃 44px 이상 보장 (WCAG 기준) |

**컬럼 그리드:** 모바일에서는 단일 컬럼 레이아웃이 원칙이다. 대시보드 위젯만 예외적으로 2컬럼 그리드(gap: 12px)를 허용한다.

**Safe Area 처리:** 모든 화면 하단에 `SafeAreaView` 적용. 탭 바가 없는 스택 화면은 하단 `pb-safe` 추가.

### 4-4. 백오피스 웹 레이아웃 그리드

| 항목 | 값 |
|------|----|
| 사이드바 폭 | 240px (고정) |
| 콘텐츠 영역 최소 폭 | 768px |
| 콘텐츠 최대 폭 | 1200px (가운데 정렬) |
| 콘텐츠 내부 padding | 32px |
| 섹션 간 여백 | 32px |
| 카드 간 여백 | 24px |
| 테이블 셀 수직 padding | 12px (16px: 중요 행) |

**반응형 브레이크포인트 (백오피스):** 1024px 미만은 사이드바 숨김 + 햄버거 메뉴로 전환. 768px 미만은 테이블을 카드형 목록으로 전환.

- Height: auto, 최소 96px (3줄), 최대 240px (자동 확장)

### 5-5. BottomSheet / Modal

#### BottomSheet (모바일 액션시트)

빌라메이트의 모바일 앱에서 가장 자주 사용되는 오버레이 패턴. 화면 하단에서 올라오는 드로어 형태.

| 속성 | 값 |
|------|----|
| 배경 | `#FFFFFF` |
| 상단 Border Radius | `rounded-t-3xl` (24px) |
| 하단 | 없음 (화면 하단까지 채움) |
| Handle | 상단 중앙 4px × 32px 회색 바 (`neutral-300`), 상단 여백 8px |
| 내부 Padding | 상단 20px, 좌우 16px, 하단 Safe Area + 24px |
| Dimmed Overlay | `rgba(0,0,0,0.5)` — 탭 시 BottomSheet 닫힘 |
| 애니메이션 | slide-up 200ms ease-out / slide-down 180ms ease-in |

**높이 유형**
- **Fixed**: 내용물 크기에 맞춤. 최소 160px, 최대 화면의 85%.
- **Scrollable**: 내용이 긴 경우 (입주민 목록, 항목 선택 등). 내부에 `ScrollView` 배치. 상단 타이틀은 sticky.
- **Full**: 화면 전체 높이 (100%). 이 경우 상단 Handle 대신 X 버튼으로 닫기.

**BottomSheet 타이틀 구조 (선택적)**
- 타이틀: `heading-3` (18px, 600), `neutral-900`
- 보조 설명: `body-sm` (13px), `neutral-500`
- 타이틀과 내용물 사이: `Divider` (`neutral-200`, 1px)

**사용 맥락 예시**
- 미납자 독촉 전 확인 ("정말 독촉하시겠습니까?")
- 청구서 유형 선택 (고정/변동)
- 날짜 선택 (DatePicker 래핑)
- 이미지 첨부 방식 선택 (카메라/갤러리)

#### Modal (센터 다이얼로그) — 확인·경고 전용

모바일에서 Modal은 최소화한다. 반드시 사용자 확인이 필요한 2가지 경우에만 사용한다: (1) 파괴적 액션 확인 (삭제, 강퇴, 투표 종료), (2) 결제 전 최종 확인.

| 속성 | 값 |
|------|----|
| 배경 | `#FFFFFF` |
| 폭 | `w-full mx-4` (좌우 16px 여백) |
| Border Radius | `rounded-2xl` (16px) |
| 내부 Padding | 24px |
| Dimmed Overlay | `rgba(0,0,0,0.6)` |
| 최대 폭 | 360px (중앙 정렬) |

**Modal 구성 요소**
- 아이콘 (선택적): 36px, 파괴적 액션은 `error-500` 컬러 경고 아이콘
- 타이틀: `heading-2` (20px, 600)
- 설명: `body-md` (15px, 400), `neutral-700`
- 버튼 영역: 2개 버튼 (취소 Secondary + 확인 Primary 또는 Destructive), 세로 배치 (위: 주요 액션, 아래: 취소) 또는 가로 배치

**백오피스 Modal:** PC 기준이므로 최대 폭 480px, 레이아웃 동일.

## 7. 모바일 UX 패턴

### 7-1. 탭 바 구조 — 상세 명세

위 6-3에서 정의한 아이콘 외 추가 규칙:

**뱃지 (알림 카운터)**
- 위치: 아이콘 우측 상단 오버레이
- 크기: 최소 16px × 16px (숫자 없는 dot), 숫자 있을 경우 20px × 20px 이상
- 색상: `error-500` 배경, White 텍스트
- 폰트: `caption` (12px, 700)
- 최대 표시: 99+

**탭 전환 애니메이션:** 즉시 전환 (별도 transition 없음). 탭 이동 시 부드러운 슬라이드나 페이드는 오히려 40~60대 사용자에게 혼란을 준다.

**탭 바 구분선:** `border-t border-neutral-200` 1px 상단 선으로 콘텐츠 영역과 분리. Shadow 사용 안 함 (탭 바가 콘텐츠 위에 떠있는 느낌 방지).

### 7-2. 빈 상태 (Empty State) 처리 패턴

**원칙:** 빈 화면은 "아무것도 없음"이 아니라 "다음 행동을 안내하는 공간"이다.

#### 구성 요소

| 요소 | 규격 | 색상 |
|------|------|------|
| 일러스트레이션 또는 아이콘 | 80px × 80px | `neutral-300` (회색 조형) |
| 메인 카피 | `heading-3` (18px, 600) | `neutral-700` |
| 서브 카피 | `body-md` (15px, 400) | `neutral-500` |
| CTA 버튼 (선택적) | Button `md` Primary | — |

#### 화면별 Empty State 메시지 지침

| 화면 | 메인 카피 | 서브 카피 | CTA |
|------|-----------|-----------|-----|
| 청구서 목록 (발행 없음) | "아직 청구서가 없어요" | "첫 번째 청구서를 발행해 입주민에게 알려보세요" | 청구서 발행하기 |
| 입주민 목록 (가입 없음) | "아직 입주민이 없어요" | "초대 코드를 공유해 입주민을 초대해보세요" | 초대 코드 보기 |
| 커뮤니티 (게시글 없음) | "아직 게시글이 없어요" | "이웃에게 첫 글을 남겨보세요" | 글쓰기 |
| 장부 (내역 없음) | "장부 내역이 없어요" | "수입이나 지출 내역을 기록해보세요" | 내역 추가 |
| 알림함 (알림 없음) | "새로운 알림이 없어요" | "중요한 소식이 오면 여기서 알려드릴게요" | 없음 |

**아이콘 선택 원칙:** 화면 도메인과 일치하는 Heroicons outline 아이콘 사용. 별도 일러스트레이션은 Phase 2 이후 고려.

### 7-3. 로딩 패턴

**원칙: 콘텐츠 유형에 따라 Skeleton과 Spinner를 구분한다.**

#### Skeleton 사용 기준

데이터의 최종 레이아웃 구조가 예측 가능할 때 사용. 사용자가 "무언가 로드되고 있다"는 사실과 "어디에 무엇이 들어올지"를 동시에 인지하게 해 체감 로딩 시간을 단축시킨다.

| 화면 | Skeleton 형태 |
|------|--------------|
| 대시보드 위젯 | 2컬럼 카드 4개 — 각 카드 내부 회색 블록 |
| 청구서 목록 | 카드형 3개 반복 — 좌측 텍스트 2줄 + 우측 뱃지 블록 |
| 커뮤니티 게시글 목록 | 아바타 원 + 제목 1줄 + 본문 2줄 블록 3회 반복 |
| 입주민 목록 | 행 높이 56px, 좌측 이니셜 원 + 이름 블록 5회 반복 |

**Skeleton 스타일**
- 기본색: `neutral-100` (#F3F4F6)
- 반짝임(Shimmer): left-to-right gradient sweep, 1.5초 반복
- Border Radius: 표시될 콘텐츠와 동일한 radius 적용

#### Spinner 사용 기준

구조가 예측 불가능하거나 즉시 완료될 것으로 기대되는 짧은 작업에 사용.

| 상황 | 사용 패턴 |
|------|----------|
| 버튼 내 제출 (폼 저장, 청구서 발행) | Button Loading State (버튼 내 Spinner) |
| 페이지 전환 초기 로드 (0.5초 미만 예상) | Spinner 화면 중앙 배치. 배경 `bg-screen`. |
| Infinite Scroll 추가 로딩 | 리스트 하단 Spinner 24px |
| Pull-to-Refresh | 시스템 기본 RefreshControl 사용 |

**Spinner 규격**
- 크기: 24px (기본), 16px (버튼 내)
- 색상: `primary-600` (독립 Spinner) / White (버튼 내 Primary 버튼)
- 두께: 2px stroke

**300ms 규칙:** 로딩이 300ms 이내 완료될 것이 확실하면 로딩 UI를 표시하지 않는다. 불필요한 깜빡임이 UX를 저하시킨다.

### 7-4. 에러 상태 처리 패턴

에러는 발생 범위에 따라 3가지로 분류한다.

#### 레벨 1: 폼 인라인 에러 (필드 수준)

- 위치: Input 컴포넌트 하단 Helper Text 영역
- 폰트: `caption` (12px), `error-500`
- 아이콘: `exclamation-circle` 12px, `error-500`, 텍스트 왼쪽에 배치
- 발생 시점: 제출 시 또는 blur 이벤트 시 (실시간 검증은 금액·날짜 등 명확한 형식만 적용)
- 예시: "관리비 금액을 입력해주세요", "날짜를 선택해주세요"

#### 레벨 2: 화면 수준 에러 (API 실패)

- 위치: 콘텐츠 영역 전체를 대체
- 구성: `exclamation-triangle` 아이콘 48px (`neutral-400`) + "불러오지 못했어요" (`heading-3`) + "잠시 후 다시 시도해주세요" (`body-md`, `neutral-500`) + "다시 시도" Button `md` Secondary
- 네트워크 오류와 서버 오류를 동일하게 처리 (사용자에게 기술적 오류 코드 비노출)

#### 레벨 3: 전체 화면 에러 (앱 크래시 수준)

- 현재 Phase에서는 React Native의 기본 에러 바운더리 사용
- Phase 2에서 커스텀 ErrorBoundary + 에러 리포팅 도입 검토

**에러 문구 원칙**
- "오류가 발생했습니다" 금지 — 사용자에게 의미가 없다
- 무슨 일이 일어났는지 + 어떻게 해결할 수 있는지를 평이한 한국어로 서술
- 기술 용어(HTTP 500, timeout 등) 비노출

### 7-5. Toast / Snackbar 패턴

**Toast 정의:** 화면 최하단(탭 바 위)에서 올라와 자동으로 사라지는 일시적 피드백 메시지.

#### 위치 및 애니메이션

- 위치: 화면 하단, 탭 바가 있을 경우 탭 바 위 8px. 탭 바 없을 경우 Safe Area 위 8px.
- 좌우 여백: 16px (`mx-4`)
- 등장: slide-up 200ms ease-out
- 사라짐: fade-out 200ms, 자동 (3초 후) 또는 수동 (X 버튼)

#### 타입별 명세

| 타입 | 배경 | 아이콘 | 사용처 |
|------|------|--------|--------|
| **Success** | `neutral-900` | `check-circle` White 20px | 저장 완료, 발행 완료, 납부 완료 |
| **Error** | `error-500` | `exclamation-circle` White 20px | 액션 실패 (발행 실패, 저장 실패) |
| **Info** | `neutral-900` | `information-circle` White 20px | 중립적 알림 (독촉 전송됨) |

**공통 속성**
- 배경 Border Radius: `rounded-xl` (12px)
- 내부 Padding: 상하 12px, 좌우 16px
- 텍스트: `label-md` (15px, 600), White
- 최대 1줄 (긴 메시지는 Toast 사용 금지 → 화면 내 인라인 메시지로 처리)
- 화면당 동시에 1개만 표시. 중첩 금지.
- 지속 시간: Success/Info = 3초, Error = 5초 (사용자가 오류 내용을 읽을 시간 확보)

**Toast vs. 화면 내 피드백 선택 기준**
- Toast: 부가적 정보 ("독촉 알림이 발송됐어요"), 즉각적인 액션 결과
- 화면 내: 사용자가 반드시 읽어야 할 중요 정보, 후속 행동이 필요한 경우
